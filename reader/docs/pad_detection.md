# 패드 검출·정합·판정 — mono 와 magenta

패드 종류마다 검출 원리가 근본적으로 다르므로 이 문서는 둘을 처음부터
끝까지 따로 서술한다. 공통 단계(회전 판정 이후)는 magenta 절에서 mono 와의
차이만 적는다.

전체 흐름은 `pipeline.py`(`_analyze_all` → `_analyze` → `_compare`)가
오케스트레이션한다. 검출만 `mode` 로 갈리고 그 뒤(회전 판정 → 정면 보정 →
품질 게이트)는 두 종류가 같은 코드를 탄다. 조도 정규화와 분진 판정만 다시
갈라진다 — mono 는 전통 경로(`normalize.py`/`dust.py`/`score.py`)를 그대로
쓰고, magenta 는 그 위에 앵커 정규화(`chroma.py`)를 덧대어 별도 지표를 낸다.
**둘 다 항상 계산한다** — magenta 패드도 mono 경로(테두리 나눗셈,
uniform/local depth)를 무조건 같이 돈다. 색 지표가 실증 전 시험 단계라 기존
지표를 잃지 않기 위해서다.

```
                              detect (mode 로 분기)
                                   │
                    ┌──────────────┴──────────────┐
                mono: detect_pads            chroma: detect_pads_chroma
              (잉크 링, 밝기 기반)              (색 블록, 채도+색상각 기반)
                    └──────────────┬──────────────┘
                                   ▼
                     방향 판정 (orient.py, 공통)
                                   ▼
                     정면 보정 (rectify.py, 공통)
                                   ▼
                     품질 게이트 (quality.py, 공통)
                                   ▼
                    ┌──────────────┴──────────────┐
              mono: normalize            mono 정규화(항상) +
              (테두리 나눗셈)              chroma: channel_normalize(앵커 2점, 유채색일 때만)
                    └──────────────┬──────────────┘
                                   ▼
                     dust 추출 (dust.py, 공통 — 두 종류 다 계산)
                                   │        chroma 만: luma_of/saturation_of
                                   ▼               ▼
                     기준 대비 비교 (_compare)
                    uniform_depth / local_depth      chroma / luma_dark / luma_light
                        (모든 패드 공통)                  (유채색 패드만)
```

## 패드 종류 판별과 `mode`

패드 종류는 두 층으로 존재한다.

- **`point.tone`** (padlab 등록 필드) — `white`/`black`/`chroma`. 어느
  개소에 어떤 패드가 붙어 있는지의 **운영 메타데이터**다.
- **`pad_type`** (padreader 결과 필드) — `mono`/`chroma`. 실제 사진에서
  **검출·판별된** 결과다.

이 둘을 구분하는 이유는 검출을 통째로 나눠 부르기 위해서다(`padlab/server/runs.py`
`plan_jobs()`) — 한 장의 사진에 mono 개소와 magenta 개소가 섞여 찍힐 수
있으므로, 개소 메타데이터로 사진을 그룹핑해 그룹마다 알맞은 검출을 두 번
호출한다.

```
point.tone == "chroma"  →  mode="chroma"  (색 블록 검출만 시도)
point.tone in ("white","black") → mode="auto" (잉크 링 검출, 사후 판별 포함)
```

`mode` 값 세 가지:

| mode | 검출 | 패드 종류 판별 | 용도 |
|---|---|---|---|
| `"auto"` (기본) | `detect_pads` (잉크 링) | 정합 후 여백 채도로 사후 판별(`classify_pad_type`) | 어떤 패드가 찍혔는지 모를 때. mono 사진에 magenta 가 섞여 있어도 mono 검출로는 안 잡히므로 실질적으로 mono 전용 |
| `"chroma"` | `detect_pads_chroma` (색 블록) | 이미 확정(색으로 찾았으므로 재판별 생략) | magenta 개소로 등록된 사진 |
| `"legacy"` | `detect_pads` | 하지 않음(항상 mono 로 고정) | 판별 로직 자체를 배제하고 싶을 때(회귀 방지용) |

`"auto"`가 magenta 를 못 찾는 이유는 이 문서 mono 절의 검출 원리를 보면
바로 나온다 — 잉크 링 검출은 밝기 대비에 의존하는데, magenta 측정면이
어둡게 찍히면(실측: 명도 13~33) 그 대비가 사라진다. 그래서 magenta 는
반드시 `mode="chroma"`로 색 기반 검출을 별도로 태워야 한다.

## mono 경로

### 검출 — `detect.py::detect_pads`

**원리**: 굵은 사각 테두리는 "잉크 링 + 그 안의 빈 구멍" 구조다. 밝기로
이진화한 뒤 컨투어 계층에서 **자식을 정확히 하나 가진 바깥 윤곽**을 요구하면
현장의 사각형 물체 대부분이 이 조건에서 떨어져 나간다.

1. **이진화 3겹 시도**. 패드 톤에 따라 극성을 통일한 뒤,
   - 사진 전체 오츠 임계 1회 (가장 흔한 경우)
   - 임계를 인쇄색 쪽으로 넓혀 재시도 (패드가 밝게 찍혀 테두리가 임계에
     걸린 사진 구제)
   - 국소(주변 평균 대비) 이진화 (요철 도장면·이음새처럼 배경이 어두워
     테두리와 배경이 한 덩어리가 되는 사진 구제)

   하나를 찾아도 나머지를 마저 시도한다 — 한 화면의 두 패드가 서로 다른
   임계에서만 보이는 경우가 실촬영에 실제로 있다. 같은 패드가 여러 단계에서
   중복으로 잡히는 것은 `geometry.quads_overlap`(중심 거리가 작은 쪽 크기의
   절반 이내면 동일 물체)으로 걸러낸다.

2. **사각 후보 필터**: `approxPolyDP` 로 정확히 4점 볼록 다각형인 것만,
   면적 비율·종횡비·solidity(면적/컨벡스헐 면적, 기본 0.85)로 추가 검증.

3. **서브픽셀 코너 정제** (`_fit_quad`): 코너 자체를 정제하지 않는다 —
   굵은 인쇄 테두리의 꼭짓점은 라운딩·잉크 번짐으로 뭉개져 `cornerSubPix`
   의 전제가 성립하지 않는다. 대신 **변마다 수백 개의 에지 교차점**을
   밝기 단면의 중간 레벨 교차로 서브픽셀 추출해 총최소자승 직선을 맞추고,
   인접한 두 직선의 교점을 꼭짓점으로 삼는다. 표본이 많아 개별 노이즈가
   평균화된다.

4. **테두리 규격 검증** (`border_matches`): 찾은 사각형이 진짜 바깥
   테두리인지 확인하는 안전장치다. 패드가 벽에서 떨어져 그림자가 지면
   그림자도 테두리만큼 어두워 사각형은 찾아지는데 한 변이 그림자 속으로
   밀려 좌표계 전체가 어긋난다 — 검출은 성공한 것처럼 보이는데 값은 조용히
   틀린, 실패보다 나쁜 상황이다. 정면으로 편 뒤 잉크 띠가 네 변 모두 0
   에서 시작해 규격 두께(예: 66/1200)에서 끝나는지로 검증한다. 안쪽
   윤곽(구멍)을 사각형으로 근사할 수 있으면 그걸로 바깥을 역산해 재시도한다.

### 판별 실패 시 사유

`FailureReason.PAD_NOT_FOUND` — 위 3겹 전부에서 규격에 맞는 링을 못 찾음.

## magenta 경로

### 검출 — `chroma.py::detect_pads_chroma`

**원리**: mono 의 밝기 기반 링 검출과 완전히 별개 경로다. mono 검출을
그대로 두고 그 옆에 새 함수로 얹었다 — 기존 무채색 판독 결과가 이 기능
추가로 흔들리면 안 되기 때문이다.

밝기에 의존하지 않는 이유: 마젠타 측정면이 어둡게 찍히면(실측 명도
13~33) 잉크와 배경의 밝기 대비가 사라져 mono 의 "링 + 구멍" 판정이 아예
성립하지 않는다. 반면 **채도는 밝기와 거의 무관하게 남는다**(같은 실측
사례에서 채도 0.91). 그래서 이쪽은 "고르게 채도가 높은 사각 덩어리"를
색으로 직접 찾는다.

1. **채도 마스크**: 화소마다 `(max-min)/max`(HSV 의 S 와 동일 정의)를
   구해 `PAD_TYPE_SATURATION_THRESHOLD`(0.35, 실촬영 무채색 최댓값 0.184의
   약 2배)를 넘는 화소만 남긴다. 열림→닫힘 형태학 연산으로 렌즈 색수차
   등 가는 잡음을 지운다.

2. **윤곽 후보**: `findContours` 로 얻은 각 윤곽에 대해
   - 면적 비율이 규격 범위(`min_pad_area_ratio`~`max_pad_area_ratio`) 안에 있는지
   - `cv2.minAreaRect` + `boxPoints` 로 최소외접사각형을 구해, 그 사각형
     면적 대비 실제 컨투어 면적(충전율)이 0.5 이상인지 — mono 의
     `min_solidity`(0.85)를 그대로 쓰지 않는다. 실촬영 색 블록은 윤곽이
     매끈하지 않아(원근·JPEG 잡음으로 5각형 등으로 과분할되기도 한다)
     `approxPolyDP` 의 "정확히 4점" 요구나 mono 수준의 충전율 요구를
     쓰면 진짜 패드까지 함께 떨어진다. minAreaRect 는 컨투어가 정확한
     사각형이 아니어도 "가장 잘 맞는 사각형"을 그대로 내주므로 이 문제가
     없다.
   - 컨투어 내부 화소의 **평균 색상각**(HSV Hue, 원형평균)이
     `MAGENTA_HUE_DEG`(324°, 인쇄 마젠타 RGB 236,0,140 에서 산출)와
     `HUE_TOLERANCE_DEG`(40°) 이내인지 — 채도만으로는 마젠타가 아닌 다른
     유채색 물체(실촬영에서 실제로 걸린 사례: 채도 높은 주황색 사무실
     파티션 원단)까지 후보가 된다. solidity 를 느슨하게 푼 대신 진짜
     판별은 색상각이 맡는다.

3. **측정면 → 패드 외곽 역산** (`_pad_corners_from_margin`): 위 과정은
   측정 여백(`spec.margin`)의 네 꼭짓점만 찾는다. 패드 외곽은 별도로
   찾지 않고 사영변환으로 역산한다 — 여백과 외곽은 같은 평면 위의 두
   사각형이므로 여백의 정규화 좌표 → 사진 좌표 변환을 구하면, 그 변환을
   외곽의 정규화 좌표 (0,0)-(1,1)에 그대로 적용해 외곽의 사진 좌표를
   얻는다. 이 방식의 전제는 인쇄 규격(`spec.margin`)이 고정돼 있다는
   것뿐이라 잉크 링을 전혀 보지 않고도 외곽을 낼 수 있다.

### 겹침 제거 — 설계 근거

같은 물체가 형태학 연산 과정에서 컨투어 두 개로 갈라지는 경우가 있다(가는
다리로 이어진 덩어리가 열림 연산에서 끊기는 등). mono 가 이진화 3겹에서
같은 패드를 중복으로 낼 수 있는 것과 같은 문제라, **같은 판정 함수를
재사용**한다(`_overlaps`를 `detect.py`에서 `geometry.quads_overlap`으로
승격). 정밀 IoU 대신 "중심 거리가 작은 쪽 크기의 절반 이내면 동일 물체"라는
느슨한 기준을 쓰는 이유는 두 사각형이 같은 패드를 서로 다른 정밀도로 맞춘
결과라 변까지 정확히 겹치지는 않기 때문이다. 후보를 면적 큰 순으로 정렬해
채우면서, 이미 채택된 것과 겹치면 버린다.

**이 겹침 제거만으로는 부족했다** — 실촬영 검증(1089 사진) 중 겹치지 않는
**진짜로 서로 다른 위치의** 오검출 4건이 나왔는데, 원인은 채도 높은
주황색 파티션 원단이 형태학 연산으로 여러 조각으로 쪼개진 것이었다. 기하
겹침 판정은 애초에 서로 다른 물체를 걸러낼 수 없으므로, 이건 겹침 문제가
아니라 **엉뚱한 색을 마젠타로 오인하는 문제**였다. 그래서 겹침 제거보다
앞단인 색상각 필터를 추가하는 것이 근본 해결이었고, 이후 minAreaRect 로
형태 판정을 낮춰야 진짜 패드가 다시 통과했다. 세 겹(겹침 제거 · 색상각 ·
형태 완화)이 서로 다른 실패 모드를 하나씩 막는다 — 어느 하나만으로는
오검출도 못 없애고 진검출도 못 살린다.

### 판별 실패 시 사유

`FailureReason.PAD_NOT_FOUND` — 채도+색상각+형태 조건을 만족하는 윤곽이
없음. mono 와 실패 사유 enum 을 공유하지만 검출 경로가 다르므로 원인
해석은 다르다(예: 채도 임계 미달이면 조명이 아니라 인쇄 발색 자체를
의심해야 한다).

### 앵커 정규화 — `chroma.py::channel_normalize`

mono 의 조도 정규화(`normalize.py`, 테두리 밝기로 나눗셈)는 그레이스케일
1채널이라 magenta 의 색 정보를 보존하지 못한다. 대신 도안에 인쇄된 **2톤
앵커 패치**(흑/백, `spec.SYNTH_PROTECTED.anchor_white`/`anchor_black`)로
R·G·B 채널을 각각 2점 캘리브레이션한다.

```
reflectance = (observed - black_median) / (white_median - black_median)   # 채널별
```

`I = g·E·ρ + B₀` 모델에서 오프셋 `B₀`와 게인·조명 `g·E`가 함께 소거된다 —
mono 의 테두리 단독 나눗셈은 `B₀`가 안 지워지고 저반사면(검은 잉크)일수록
그 비중이 커지는 한계가 있는데, 이 방식은 그 한계가 없다. 앵커 좌표는
`cfg.spec` 설정과 무관하게 `SYNTH_PROTECTED` 고정값을 쓴다 — 유채색 패드의
물리적 앵커 위치는 도안 자체의 고정 사실이라 흑백 규격 설정을 따라가면
안 된다.

**클리핑 검사**: 앵커 화소가 하나라도 정확히 0 또는 255 면
`FailureReason.ANCHOR_CLIPPED` 로 전체 판독을 실패시킨다. 카메라 8비트
양자화 한계 그 자체이지 임계값이 아니다 — 클리핑된 화소는 실제 반사율을
잃어버린 것이라 부분적으로도 신뢰할 수 없다. 흑백 span 이 0 이하이면
`ANCHOR_SPAN_INVALID`. 두 사유 다 "조용히 틀린 값" 대신 판독 자체를
막는다.

### 판정 로직 — `chroma / luma_dark / luma_light`

정규화된 반사율 위에서 두 축을 낸다(둘 다 `optical_density.py`와 같은
"자유 파라미터 없음" 설계 — 임계값·top-N 선택·가중합 없이 노출 영역 전체를
부호 그대로 합산 → 평균 → 제곱근):

- **`chroma`**: 채도(`saturation_of`, 정규화 반사율 위의 `(max-min)/max`)가
  기준 대비 얼마나 줄었는지. 마젠타 잉크는 무채색 분진이 앉으면 채도가
  떨어지므로 방향은 하나(감소)뿐이다.
- **`luma_dark` / `luma_light`**: 명도(`luma_of`, Rec.601)는 흑색 분진(어두워짐)과
  백색 분진(밝아짐)이 서로 상쇄되므로 부호로 갈라 각각 낸다. 분모(N)는
  두 방향 모두 노출 영역 전체 픽셀 수로 같게 둬, 국소적으로만 밝아지거나
  어두워져도 전체 면적 대비 등가 깊이가 나오게 한다.

세 지표 모두 **판정에 쓰지 않는 시험 지표**다 — `success`/`FailureReason`
은 이 값들을 보지 않는다. `pad_type`이 `chroma`일 때만 응답에 실린다(항상
계산해 응답 크기를 부풀리지 않기 위해 `PadResult`의 chroma 필드는
`pad_type == "chroma"`일 때만 채운다).

## mono/magenta 공통 — 회전 판정 · 정면 보정 · 품질 게이트

검출 이후는 두 종류가 같은 코드를 그대로 탄다. 검출 함수가 이미 각자의
원리로 "패드 외곽 네 꼭짓점"이라는 같은 형태의 결과(`Detection`)를 내놓기
때문이다.

- **회전 판정** (`orient.py`): 모서리 블록 3곳(TL/TR/BL)은 인쇄돼 있고
  BR 은 비어 있다. 잠정 순서로 작게 정면 보정한 뒤 네 자리의 "잉크
  정도"를 재 가장 낮은 자리를 빈 자리로 판정한다. 판정 신뢰도(마진)는
  "빈 자리와 그 다음 자리의 차" ÷ "잉크-바탕 전체 대비"로, 조명·노출과
  무관한 값이다. 마진이 `cfg.orient.min_margin` 미달이면
  `ROTATION_AMBIGUOUS`로 실패.
- **정면 보정** (`rectify.py`): 회전 판정으로 바로잡은 꼭짓점 순서로
  `getPerspectiveTransform` + `warpPerspective`. 이후 모든 ROI 는
  `spec.py` 의 정규화 좌표 × 출력 크기로 결정된다. 축소율이 크면
  `INTER_AREA` 로 먼저 정수배 다운샘플한다(그냥 warp 하면 화소가 솎여
  여백에 없는 얼룩이 생긴다 — 분진 신호와 구분이 안 되는 오염원이라
  피한다).
- **품질 게이트** (`quality.py`): 원본 이미지에서(정면 보정은 warp 보간이
  스케일을 선명도에 섞으므로) 에지 상승 거리 비율·Tenengrad·포화율·패드
  픽셀 크기를 재고, `cfg.quality`의 임계와 비교한다. magenta 도 이 게이트를
  그대로 통과해야 한다 — 색이 있어도 흐리거나 노출이 극단이면 신뢰할 수
  없다는 전제는 같다.

두 종류가 같은 사진에 함께 찍혀도 각 `mode` 호출은 자신의 검출 방식에
해당하는 것만 낸다 — mono 검출은 magenta 를 링으로 못 찾고, chroma 검출은
채도 임계 미만인 mono 패드를 못 찾는다. padlab 은 개소 메타데이터로
사진을 그룹핑해 필요한 `mode` 로 각각 호출하고, 결과를 개소 번호로 다시
합친다(`padlab/server/runs.py::plan_jobs`/`process_capture`) — 한 사진
안에서 두 검출이 서로의 결과를 침범하지 않으므로 병합은 단순 합집합이다.

## 기준(baseline) 대비 — `_compare`

패드 종류가 판독 사진과 기준 사진에서 다르게 판별되면(예: 조명 문제로
한쪽만 mono 로 오판) `FailureReason.PAD_TYPE_MISMATCH`로 실패시킨다 — 서로
다른 정규화 체계로 낸 값을 비교하면 의미가 없기 때문이다. 이후
`uniform_depth`/`local_depth`는 두 종류 모두에서 계산되고,
`chroma`/`luma_dark`/`luma_light`는 `pad_type == "chroma"`일 때만
추가로 계산된다.
