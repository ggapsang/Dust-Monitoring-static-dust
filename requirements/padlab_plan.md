# 참조 패드 판독 실험 관리 웹 기획안

작성일: 2026-08-20
대상: 판독 실험 관리 서버 개발 담당자

전제: 판독 모듈의 `TARGET_ID` 명칭이 `POINT_ID` 로 변경된 상태를 기준으로 한다.

---

## 1. 배경과 목적

참조 패드 판독 모듈(`padreader`)과 판독 서비스(`padservice`)는 완성되어 있으나,
임계값이 대부분 비어 있어 실증 데이터로 채워야 하는 단계다. 현재 실증은 다음
절차를 사람이 반복한다.

1. `/docs` 에서 기준 사진과 판독 사진을 올려 판독을 실행한다
2. 응답 JSON 을 눈으로 읽는다
3. 결과 이미지 주소 3개를 각각 열어 확인한다
4. 값과 이미지를 문서 도구에 옮겨 적는다

결과 이미지는 보관 시간이 지나면 사라지므로 확인 시점이 강제되고, 판독 건수가
늘수록 옮겨 적는 비용이 판독 자체보다 커진다. 개소별 회차 추이나 지표 분포는
옮겨 적은 뒤에야 볼 수 있어 실증 루프가 길다.

본 기획의 목적은 이 절차를 웹 화면과 영속 저장소로 대체하는 것이다. 판독을
화면에서 실행하고, 결과와 이미지를 영구 보관하며, 누적된 판독 결과를 표·시계열·
분포로 조회한다.

AMR 순회가 아직 없으므로 촬영과 촬영 조건 지정은 사람이 한다.

## 2. 시스템 구성

```
브라우저
   |
   v
판독 실험 관리 서버 (신규)  --HTTP-->  padservice (8911)
   |                                      |
   +--> PostgreSQL                        +--> padreader
   +--> 이미지 저장소 (공유 볼륨) <--------+
```

`padreader` 는 무상태 순수 함수를 유지한다. 시계열 저장, 기준 사진 관리, 식별자
대응, 화면은 전부 신규 서버가 맡는다. `padservice` 는 판독 요청 인터페이스로만
사용하며 수정하지 않는다.

신규 서버는 이미지 저장소를 `padservice` 와 공유 볼륨으로 나눠 갖고, 판독은
`POST /read/path` 로 경로를 넘겨 요청한다. 업로드 본문으로 재전송하지 않는다.

판독 설정은 서버 고정값(`config/default.yaml`)을 기본으로 쓴다. 화면에서 서버
설정을 변경하지 않는다. 사후 비교가 필요한 경우에 한해 요청별 오버라이드를
지정해 재판독한다.

## 3. 식별자 체계

두 식별자를 사전에 등록하고 대응 관계를 정의한다.

- **TARGET_ID** — AMR 촬영 단위. 한 웨이포인트에서 PTZ 프리셋을 잡고 촬영하는
  사진 한 장에 대응한다. 에코프로비엠·로아스 체계에서 사용하는 값이다
- **POINT_ID** — 패드가 부착된 물리적 관측 개소. 패드에 인쇄된 번호다

TARGET_ID 하나에 POINT_ID 여럿이 속한다(1:N). 사진 한 장에 패드가 여러 개
찍히는 경우가 여기에 해당한다.

판독 실행 시 사람은 사진마다 TARGET_ID 를 지정한다. 서버는 그 TARGET_ID 에
등록된 POINT_ID 들의 기준 사진을 모아 판독 요청에 함께 넘긴다. 사람이 지정한
TARGET_ID 가 정본이며, 판독기가 읽어 낸 POINT_ID 는 판독 모듈이 기준 패드와
짝짓는 데 쓰인다.

짝짓기 결과의 해석은 판독 모듈의 기존 원칙을 그대로 따른다. 짝을 찾지 못한
패드는 실패 사유와 함께 결과에 남으므로, 서버는 그 결과를 가공하지 않고 저장한다.

패드 톤은 개소별 분진 색상이 고정이므로 POINT_ID 등록 정보에 둔다. 판독 실행
시 사람이 매번 지정하지 않는다.

## 4. 데이터 모델

PostgreSQL 단일 인스턴스. 판독 응답 원본은 `jsonb` 로 통째로 보관하고, 조회에
쓰는 항목만 별도 컬럼으로 승격한다. 응답 스키마가 바뀌어도 과거 판독 결과를
잃지 않기 위해서다.

### target — 촬영 단위

| 컬럼 | 설명 |
|---|---|
| `target_id` | PK. 에코프로비엠 체계의 값 |
| `name` | 표시 명칭 |
| `location_desc` | 촬영 위치 설명 |
| `note` | 비고 |

### point — 관측 개소

| 컬럼 | 설명 |
|---|---|
| `point_id` | PK. 패드에 인쇄된 번호 |
| `target_id` | FK. 이 개소가 찍히는 촬영 단위 |
| `name` | 표시 명칭 |
| `location_desc` | 물리적 위치 설명 |
| `tone` | 패드 톤. `white` / `black` |
| `note` | 비고 |

### baseline — 기준 사진

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `point_id` | FK |
| `file_path` | 기준 사진 파일 경로 |
| `effective_from` | 부착 일시. 이 시각 이후 촬영분에 적용된다 |
| `superseded_at` | 후속 기준으로 대체된 일시. 현행 기준은 `null` |
| `registered_at` | 등록 일시 |

개소당 현행 기준은 한 건이다. 패드를 교체하면 새 기준을 등록하고 이전 기준은
이력으로 남긴다. 판독 사진에 적용할 기준은 촬영 일시로 선택한다.

기준 사진 파일은 한 디렉터리에 모아 두고 POINT_ID 로 색인한다.

### capture — 판독 사진

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `target_id` | FK. 사람이 지정한 값 |
| `file_path` | 사진 파일 경로 |
| `captured_at` | 촬영 일시. 사람이 지정 |
| `uploaded_at` | 업로드 일시 |
| `note` | 비고 |

### run — 판독 실행

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `executed_at` | 실행 일시 |
| `config_override` | `jsonb`. 요청에 얹은 오버라이드. 없으면 `{}` |
| `source_run_id` | 재판독인 경우 원본 실행 |
| `kind` | `initial` / `rerun` |

### reading — 판독 결과

판독 응답이 패드마다 한 건씩 목록으로 오므로, 한 `capture` 에 여러 `reading` 이
달린다.

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `run_id` | FK |
| `capture_id` | FK |
| `baseline_id` | FK. 짝지어진 기준. 실패 시 `null` |
| `point_id` | FK. 짝지어진 개소. 실패 시 `null` |
| `success` | 판독 성공 여부 |
| `failure_reason` | 실패 사유 |
| `failure_detail` | 실패 상세 |
| `summary` | 응답의 한 줄 요약 |
| `score_uniform` | 고르게 오염된 정도 |
| `score_localized` | 한 군데가 심하게 오염된 정도 |
| `score_combined` | 종합 지표 |
| `quality_sharpness` | 선명도 |
| `quality_saturated_ratio` | 포화 픽셀 비율 |
| `quality_pad_size_px` | 패드 픽셀 크기 |
| `quality_pad_size_diff_ratio` | 기준과의 패드 크기 차이 비율 |
| `read_point_id` | 판독기가 읽어 낸 개소 번호 |
| `read_point_confidence` | 그 확신도 |
| `elapsed_ms` | 처리 시간 |
| `response` | `jsonb`. 응답 원본 |
| `img_baseline_rectified` | 기준 정합 이미지 경로 |
| `img_rectified` | 판독 정합 이미지 경로 |
| `img_distribution` | 오염도 분포 이미지 경로 |

`read_point_id` 와 `point_id` 를 함께 둔다. 짝짓기 결과와 판독값을 분리해 두어야
번호 오독이 있었는지를 나중에 셀 수 있다.

## 5. 파일 저장

DB 에는 경로만 둔다. 파일은 공유 볼륨에 저장한다.

```
/data/baselines/<POINT_ID>/<baseline_id>.<ext>
/data/captures/<촬영일자>/<capture_id>.<ext>
/data/results/<reading_id>/{baseline_rectified,rectified,distribution}.png
```

결과 이미지는 `padservice` 응답에 담긴 주소에서 즉시 내려받아 위 경로에 복사한다.
판독 트랜잭션 안에서 처리하며, 복사에 실패하면 해당 `reading` 의 이미지 경로를
비워 두고 나머지는 저장한다. `padservice` 의 이미지 보관 시간이 지나면 같은
주소를 다시 얻을 수 없다.

## 6. 판독 실행

한 번의 실행에 사진 여러 장을 올려 일괄 판독한다.

1. 사람이 사진 여러 장을 올리고, 사진마다 TARGET_ID 와 촬영 일시를 지정한다
2. 서버가 사진을 저장소에 쓰고 `capture` 를 만든다
3. 사진마다 해당 TARGET_ID 에 속한 POINT_ID 를 조회하고, 각 개소에서 촬영
   일시에 유효한 기준 사진 경로를 모은다
4. `POST /read/path` 를 호출한다. `path` 는 판독 사진, `baseline_path` 는 3에서
   모은 경로 목록, `tone` 은 개소 등록 정보의 값이다
5. 응답의 패드별 결과를 `reading` 으로 저장하고, 결과 이미지를 내려받아 복사한다

한 TARGET_ID 에 속한 개소들의 톤이 서로 다르면 톤별로 나눠 호출한다.

기준 사진이 등록되지 않은 개소, 촬영 일시에 유효한 기준이 없는 개소는 판독
요청에서 제외하고 그 사실을 실행 결과에 남긴다.

실행 진행 상황은 사진 단위로 표시한다. 한 장이 실패해도 나머지를 계속 처리한다.

## 7. 재판독

저장된 원본 사진 경로가 남아 있으므로, 사후 비교는 파일 재업로드 없이 수행한다.

1. 대상 판독 결과를 선택한다. 한 건 또는 실행 단위 전체
2. 설정 오버라이드를 JSON 으로 입력한다
3. 서버가 같은 `capture` 와 같은 `baseline` 으로 `POST /read/path` 를 다시
   호출하고, `kind = rerun` 인 새 `run` 아래에 결과를 쌓는다

기존 결과를 덮어쓰지 않는다. 화면에서는 원본 실행과 재판독 실행의 지표를 나란히
비교한다.

## 8. 화면

디자인은 다임리서치 디자인 가이드를 따른다. 색상은 의미 기반 토큰으로 참조하고
HEX 직접 사용을 금지한다. Base : Contents : Accent = 6 : 3 : 1 비율 원칙을 적용한다.
상태 표시를 최상위 위계에 둔다.

진입 화면은 판독 결과 누적 스프레드시트다. 실증 단계에서 가장 자주 보는 것이
누적된 지표 값이기 때문이다.

### 8.1 촬영 단위·개소 등록

TARGET_ID 와 그 아래 POINT_ID 를 등록하고 대응 관계를 관리한다. 개소마다 명칭,
물리적 위치 설명, 패드 톤을 지정한다.

TARGET_ID 를 트리 형태로 펼쳐 소속 개소를 함께 보인다. 개소별 기준 사진 등록
여부를 같은 화면에서 표시한다.

### 8.2 기준 사진 등록

개소를 선택해 기준 사진을 올린다. 부착 일시를 함께 지정한다.

등록 시 해당 개소의 기존 현행 기준을 대체 처리하고 이력으로 남긴다. 개소별로
현행 기준과 과거 기준 이력을 함께 보인다.

기준 사진에 패드가 하나만 담기도록 안내 문구를 화면에 둔다. 여러 개가 담기면
개소마다 부착 시점이 달라지는 문제가 생긴다.

### 8.3 판독 실행

사진 여러 장을 한꺼번에 올린다. 올린 사진마다 TARGET_ID 와 촬영 일시를 지정하고,
필요 시 설정 오버라이드를 JSON 으로 입력한다.

실행 후 사진별 처리 상태와 판독된 패드 수, 성공·실패를 목록으로 보인다. 실행이
끝나면 결과 스프레드시트로 이동한다.

### 8.4 판독 결과 누적 스프레드시트

한 행이 판독 결과 한 건이다. 전체 판독 이력을 표로 보인다.

열: 촬영 일시, TARGET_ID, 개소, 회차, 성공 여부, 실패 사유, uniform, localized,
combined, 선명도, 포화 비율, 패드 크기, 패드 크기 차이 비율, 판독 개소 번호,
확신도, 처리 시간, 실행 구분, 오버라이드 유무.

필터: 기간, TARGET_ID, 개소, 성공 여부, 실패 사유, 실행 구분.
정렬: 모든 수치 열.
CSV 내보내기를 제공한다.

행을 선택하면 사진쌍 상세로 이동한다.

### 8.5 사진쌍 상세 조회

한 판독 건의 기준 사진과 판독 사진, 결과 이미지 3종, 전체 지표를 함께 본다.

여러 건을 선택해 리스트형으로 세로로 이어 붙여 볼 수 있다. 같은 개소의 회차별
분포 이미지를 위아래로 나열해 비교하는 것이 실증에서 가장 자주 필요한 조회다.

각 항목에 적용된 설정 오버라이드를 함께 표시한다. 이 화면에서 재판독을 실행할
수 있다.

### 8.6 개소별 회차 시계열

개소를 선택해 촬영 일시 순으로 지표 추이를 본다. 회차는 촬영 일시 순서로 매긴다.

세 축을 함께 보인다.

- **절대량** — 기준 대비 지금까지 쌓인 총량. `score_combined` 원값
- **추세** — 직전 회차 대비 증분
- **누적** — 증분에서 여유를 뺀 값의 합(CUSUM)

추세의 이상 경계는 개소마다 자기 이력에서 낸다(증분의 중앙값 + n × MAD).
n 과 CUSUM 여유값, 등급 경계는 설정으로 두고 값은 실증 분포를 보고 채운다.
값이 비어 있는 동안에는 경계선을 그리지 않고 계열만 보인다.

포인트 간 스코어 직접 비교는 하지 않는다. 이 화면은 개소 하나를 대상으로 하며,
여러 개소를 한 좌표축에 겹쳐 그리지 않는다.

### 8.7 지표 분포

임계값을 정하기 위한 화면이다. 지표 하나를 선택해 누적 판독 결과의 분포를
히스토그램으로 보이고, 최소·중앙·최대를 함께 표시한다.

대상 지표: uniform, localized, combined, 선명도, 포화 비율, 패드 크기,
패드 크기 차이 비율, 회전 판정 마진, 개소 번호 판독 확신도, 처리 시간.

산출값은 게이트 통과 여부와 무관하게 항상 나오므로, 성공 건과 실패 건을 색으로
구분해 같은 축에 겹쳐 그린다. 어느 값에서 실패가 갈리는지를 보기 위해서다.

실패 사유별 건수를 함께 보인다.

기간과 개소로 필터링한다.

## 9. API

신규 서버가 제공하는 인터페이스다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` `POST` `PATCH` `DELETE` | `/api/targets` | 촬영 단위 등록·조회·수정·삭제 |
| `GET` `POST` `PATCH` `DELETE` | `/api/points` | 개소 등록·조회·수정·삭제 |
| `GET` `POST` | `/api/baselines` | 기준 사진 등록·조회 |
| `GET` | `/api/baselines/current` | 개소별 현행 기준 조회 |
| `POST` | `/api/runs` | 판독 실행. 사진 여러 장과 메타데이터 |
| `POST` | `/api/runs/{id}/rerun` | 오버라이드를 얹은 재판독 |
| `GET` | `/api/runs/{id}` | 실행 상태와 결과 요약 |
| `GET` | `/api/readings` | 판독 결과 목록. 필터·정렬·페이지 |
| `GET` | `/api/readings/{id}` | 판독 결과 단건 |
| `POST` | `/api/readings/rerun` | 선택한 판독 건들의 재판독 |
| `GET` | `/api/readings/export.csv` | 현재 필터 조건의 CSV |
| `GET` | `/api/series/{point_id}` | 개소별 시계열. 절대량·추세·누적 |
| `GET` | `/api/distribution` | 지표 분포 |
| `GET` | `/files/...` | 저장된 이미지 |

## 10. 배포

Docker Compose 로 네 개 서비스를 올린다.

| 서비스 | 내용 |
|---|---|
| `padservice` | 기존 판독 서비스. 이미지 저장소 볼륨을 읽기 전용으로 마운트 |
| `padlab` | 신규 서버. 이미지 저장소 볼륨을 읽기·쓰기로 마운트 |
| `postgres` | 영속 저장소 |
| `web` | 정적 화면 |

볼륨은 이미지 저장소와 PostgreSQL 데이터 두 개다. 판독 설정 파일과 폰트 폴더는
기존과 같이 `padservice` 에 마운트한다.

`padlab` 은 `padservice` 주소와 DB 접속 정보를 환경변수로 받는다. 기동 시
`padservice` 의 `GET /healthz` 와 `GET /config` 를 호출해 연결과 적용 설정을
확인하고, 실패하면 기동하지 않는다.

사무실 내부망 단일 인스턴스로 운영한다.
