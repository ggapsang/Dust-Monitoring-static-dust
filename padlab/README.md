# 판독 실험 관리 서버

판독 결과를 쌓아 두고 화면에서 보는 곳이다. **판독은 하지 않는다** — 사진
경로를 `padservice` 에 넘겨 부르고, 돌아온 값과 이미지를 저장한다.

현장에 가면 상위 시스템이 이 자리를 대신한다. 실증 단계에서 임계값을 채우기
위한 도구이므로, 판독 모듈(`reader/`)과 섞이지 않게 따로 두었다.

## 띄우기

    docker compose up -d --build
    http://localhost:8912/

`padservice` 와 PostgreSQL 이 함께 뜬다. 기동할 때 판독 서비스의 `/healthz` 와
`/config` 를 확인하고 실패하면 기동하지 않는다 — 붙을 곳을 못 찾은 채 떠
있어 봐야 첫 판독에서 깨지는데, 그때는 사진을 이미 올린 뒤다.

## 쓰는 순서

- **등록** 에서 촬영 단위(TARGET_ID)와 개소(POINT_ID)를 넣는다. 개소마다 패드
  톤을 정한다. 어두운 분진이면 white, 밝은 분진이면 black 이다
- 개소마다 **기준 사진** 을 올린다. 부착 직후 깨끗할 때 찍은 것이며 패드가
  하나만 담겨야 한다
- **판독 실행** 에서 순회 사진을 한꺼번에 올린다. 파일명이 규칙에 맞으면
  촬영 단위와 일시가 자동으로 채워진다
- **결과** 에 값이 쌓인다. 행을 누르면 사진과 결과 이미지를 함께 본다

## 파일명 규칙

파일명이 곧 메타데이터 입력이다. 수십 장을 올리면서 화면에서 하나씩 지정하는
것은 `/docs` 를 두드리는 것과 비용이 같다.

    판독 사진   C_<TARGET_ID>_<YYMMDD>_<HHMM>_<nn>.jpg      C_T0042_260818_1430_01.jpg
    기준 사진   B_<POINT_ID>_<YYMMDD>_<HHMM>_r<n>.jpg       B_1079_260818_0930_r1.jpg

구분자는 `_` 고정이고 필드 안에 `_` 를 쓰지 않는다. 파싱에 실패해도 거부하지
않는다 — 그 사진만 사람이 지정한다. 값의 정본은 화면에서 확정된 것이다.

기준 사진의 `r<n>` 은 참고값이다. 현행 기준 판정은 부착 일시 순서로 한다 —
같은 정보를 두 곳에 두면 어긋났을 때 어느 쪽을 믿을 근거가 없다.

## 아는 것과 모르는 것

- **개소 간 스코어를 직접 견주지 않는다.** 촬영 거리·각도·조명이 개소마다
  달라 감도가 다르다. 회차 추이 화면은 개소 하나만 그린다
- **실패 사유의 한글 표기를 만들지 않는다.** 판독 응답의 `summary` 에 이미
  들어 있다. 화면 표시는 그것을 쓰고, 필터·집계는 원문 사유로 한다
- **판독 설정을 여기서 바꾸지 않는다.** 서버 고정값을 쓰고, 비교가 필요할
  때만 요청별 오버라이드를 얹어 재판독한다. 기존 결과는 덮어쓰지 않는다

## 환경변수

| 이름 | 기본값 | 설명 |
|---|---|---|
| `PADLAB_DATABASE_URL` | 없음 | 없으면 기동하지 않는다 |
| `PADLAB_PADSERVICE_URL` | `http://padreader:8911` | 판독 서비스 주소 |
| `PADLAB_DATA_DIR` | `/data` | 이미지 저장소. **두 컨테이너가 같은 경로여야 한다** |
| `PADLAB_CONCURRENCY` | `2` | 동시 판독 수. CPU 바운드라 늘려도 선형으로 빨라지지 않는다 |
| `PADLAB_TIMEOUT_SEC` | `120` | 판독 요청 타임아웃 |
